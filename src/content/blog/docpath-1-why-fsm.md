## 起点：智能体的短板不是写代码

过去一年，我几乎所有的编码工作都和 AI 智能体一起完成。用得越深越确认一件事：**它的短板从来不是「会不会写这段代码」**。局部实现、单点修复、写个组件，智能体已经比大多数人快。

真正的短板在工程侧——把一个跨越几天、十几个步骤的任务从头到尾做对。反复出现的事故有三类：

- **幻觉**：编造不存在的接口、文件路径，或者自信地引用一个从未写过的函数；
- **偏离目标**：做到第五步，忘了第一步定下的验收标准，产出一个「看起来完成」的东西；
- **污染代码库**：把半成品、调试代码和无关改动混进同一个提交。

这三类事故的共同根源，是任务的**状态活在对话里**。而对话记录是最差的记忆介质：易失、昂贵、无法校验。

## 核心想法：把文档变成状态机

DocPath 的做法一句话能说完：**把开发任务抽象成有限状态机（FSM），用文档承载状态的每一次迁移**。

```text
Backlog 需求池 → Spec 规格 → Plan 步骤规划 → Execution 执行
      → 门禁（Check → Review → Journal）→ Git 安全提交
```

每个任务从需求池被「提升」为 Spec，Spec 生成 Plan，Plan 拆成步骤 S1…Sn；智能体认领步骤、编码、过门禁，最终由工具（而不是它自己）宣布任务完成。命令就是状态迁移：`start S1` 是认领，`step done` 是完成一步，`done` 是触发收口门禁序列。

## 双载体：机器真源与人读视图

状态存两份，各司其职：

- **JSON / JSONL 是机器真源**：`state.json` 记录当前状态、活跃步骤、门禁结果；`breadcrumb.jsonl` 是追加式的进度事件流。
- **Markdown 是人类视图**：`spec.md`、`plan.md`、进度时间线，由结构化状态渲染而来，人随时可以打开看懂机器在干嘛。

为什么不直接上数据库或者看板服务？三个理由：

1. 智能体的母语是文本，Markdown 是所有模型都能可靠读写的格式；
2. 文档天然活在 Git 里，版本化、审计、回滚全部免费；
3. 零部署——一个 CLI 就够，任何项目 `init` 即用。

这套设计之后，「文档」不再是交付物的附属品，而是协作本身的状态存储：**文档即状态机，命令即迁移，门禁即校验**。

## 这只是起点

状态机解决了「状态存哪、怎么迁移」，但还有三个问题悬着：不是所有任务都值得走全流程（渐进式）；智能体的每一次往返都有成本（上下文经济学）；多个智能体同时干活怎么不打架（并发隔离）。这是接下来两篇的主题。
