系列第一篇说过：风控看的不是单点，是**矛盾**。所以指纹浏览器的核心工程不是「藏」，而是**让每个身份在逻辑上成立**。这篇讲我们怎么做「自洽人设」。

## 人设不是参数包，是推理链

一个人设的核心假设只有几个：操作系统、GPU 型号、语言、时区、屏幕。其余所有参数都应该**从这几个假设推导出来**，而不是独立随机。几个真实的交叉校验：

- **GPU ↔ CPU 核心数**：GPU 报 Apple M1 Pro，那 CPU 核心数必须是 10——该型号全系如此。配成 8 核，就是一台现实中不存在的机器；
- **osVersion ↔ UA**：`osVersion=10.0` 但 UA 写 `Windows NT 6.1`，内核会推导出 `platformVersion=7`，自相矛盾；
- **时区 ↔ 代理 IP**：时区设在东京，IP 就得在东京，这是外部可验证项。

推导链的意义在于：**随机性只允许出现在不会互相出卖的维度上**。噪声可以加在种子派生的地方，但结构性参数（核心数、版本、平台特征）必须收敛到同一个故事。

## 三版本一致律

指纹浏览器有一个特有的坑：**同一件事被记录在三个地方**——

```text
内核二进制的真实版本  ≠  profile 的 userAgent 字段  ≠  数据库里的 browser_core 快照
```

第二篇讲的「Client Hints 打脸」只是冰山一角。更隐蔽的是数据库快照：`browser_cores` 表里存的是**落库时的版本快照**，内核二进制升级后它不会自动变——于是下拉框里只有旧版本可选，选它就回到 UA 与内核的矛盾。

我们的处置是把「对齐」做成机制而不是人工操作：读取内核列表时按真实二进制重新探测并回写；升级后对存量 profile 跑一次幂等迁移（先 dry-run、有改动才备份、逐条记录，第二次运行必须报零改动——否则说明还有写入路径在产生旧值）。

## 配置层与内核层的分工

指纹参数体系（我们叫 lumi.conf）管**每个身份一份**的配置：平台、硬件、网络、噪声开关。内核层（基于 fingerprint-chromium 的补丁集）管**注入的时机与深度**——参数在内核启动时就生效，而不是页面加载后打补丁。

工程上有个反直觉的教训：**别猜内核支持什么参数**。主可执行文件只是个 86KB 的启动器，真实代码在 Framework 里，把二进制 `strings` 出来才能拿到权威的 `--fingerprint-*` switch 表。我们踩过的坑包括：给一个不存在的字体开关传参（静默忽略，零效果）、用 144 之前版本的 GPU 参数（144 起已移除）。**表外的参数一律不存在，而 Chromium 对未知参数不报错**——这比报错危险得多。

## 版本地狱：升级的两难

内核版本升级从来不是「换个新」：

- 144 起移除了旧的 GPU 指定参数，改用 `--disable-spoofing` 体系；
- 148 起 GPU 型号改由种子派生（不再可指定）、`deviceMemory` 按种子从 8/16/32 随机——**升级会改变存量账号环境的指纹**；
- 150 修了旧问题、引入了新回归，而且没有 macOS 构建。

所以每次升级都是一次权衡：真实度提升 vs 既有环境抖动。我们的原则是**审计站全量回归**当验收——第二篇那一套——不过关就不放量。

## 两条写入路径

最后一个容易烂尾的地方：配置的**入口不止一个**。REST API 和桌面 UI 是两条独立的写入路径，修默认值和校验时必须两条都覆盖，否则界面上新建的窗口仍然带着「前端构造什么就存什么」的旧矛盾。判据很简单：用 API 读回 UI 刚建的 profile，看关键字段有没有跟随内核。

## 小结

自洽工程做到最后，拼的不是对抗的烈度，而是**约束的完备性**：每一对可能互相出卖的参数之间，都应该有一条机器可校验的约束。做到了，身份才「像一台真的机器」。
