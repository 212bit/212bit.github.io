[DocPath 设计手记](/blog/docpath-1-why-fsm/) 系列讲的是这个工作流引擎怎么造出来的。这篇讲一个还没实现的决定：如果用它管理「非代码」的事情——项目推进、运营策划、技术预研——应该怎么办？

两条路：在 DocPath 里扩展出领域能力，或者新建一个专做管理的工作流项目。第二个问题让事情更有意思：**现在有了 AI，「新建项目」半天就能搓出来——这个变化，会不会让「扩展」显得多余？**

我的结论恰恰相反：AI 让两条路都变便宜了，但让「原地扩展」便宜得更多。下面是推演过程。

## 一、先算共性：两个领域差多少

把两种场景放进同一张表，逐阶段对照：

| 工作流阶段 | 写代码 | 管项目 |
| --- | --- | --- |
| 意图捕获 | 收需求进 backlog | 收「Q3 大促策划」进 backlog |
| 方案与决策 | 技术选型、边界、验收标准 | 目标拆解、资源、风险、决策简报 |
| 计划拆分 | S1 接口 → S2 单测 | S1 预算报批 → S2 物料设计 |
| 过程跟踪 | 认领、完成、阻塞、恢复 | 同一套语义，一字不改 |
| 门禁与验收 | 跑测试、编译、架构校验 | 交付物齐全性、指标回填、审批签署 |
| 归档复盘 | 避坑规则、技术 ADR | 复盘总结、SOP、业务决策 ADR |

一眼可见：**真正绑定「代码」的只有第五步的检查手段**。其余全是通用的——并发隔离、上下文预算、事件时间线、真源与视图分离，这些底座能力跟「管的是代码还是策划案」毫无关系。

## 二、底座才是资产，业务只是皮

DocPath 里真正难的东西，都不是业务功能，而是踩过坑才长出来的防撞梁：并发进程下的文件排他锁与防死锁、只读环境里的韧性降级、上下文预算的双计解耦与阈值自愈、机器真源与人类视图的分离与自愈、每一步动作可追溯的事件流。

新建一个「管理版」意味着这些坑一条都不会少，全部会以随机的方式重新爆一遍。更糟的是：以后在代码侧修好的底层缺陷，管理侧还带着旧版本——**一次修复变成两份维护**。

业务逻辑是最便宜的部分；底座是那 90% 看不见的成本。

## 三、AI 改变的是扩展的成本，不是扩展的必要性

传统时代大家爱新建，理由很实在：在老系统里做抽象、解耦、插件化，是重活，还容易改出回归——不如复制一份改改。

但 AI 最擅长的恰恰是重构与解耦。要求把「代码专有的门禁」剥离成可插拔的适配器、再加一层领域配置，这在今天可能就是一两个标准任务的事。**「原地扩展」从一周起的重活，变成了半小时级的小活。**

于是真正的比较变成了长期回报：

- **新建**：第一天很爽，之后是两套 CLI、两套 AGENTS.md、两套规则、两套技能文档。而 Agent 在多工具环境里最容易犯的错，就是混淆参数、目录与状态语义——**工具碎片化本身就是幻觉源**；
- **扩展**：一套协议打天下。人学一次，Agent 吃一套收敛的运行时协议；所有已有的沉淀（规则库、健康检查、文档索引）立刻对新领域生效。

统一协议的复利，是这类决策里最容易被低估的东西。

## 四、落地思路：内核不动，门禁解耦

推演下来，最省事的路径是四步：

1. **配置加领域维度**：`domain: software | management | research`，默认 software，现有行为完全不变；
2. **抽象 GateAdapter**：把 check / review 变成接口——`software` 沿用测试、编译、架构校验，`management` 换成交付物核验；
3. **管理门禁只做可证实的断言**：文件在不在、字段全不全、审批节点到没到——不碰「效果好不好」这种主观判断；
4. **规则路由**：`rules/` 里从代码规范换成业务红线与合规要点，目录结构不动。

管理模式的检查输出大概长这样：

```text
✓ campaign-plan.md 存在，结构符合约定
✓ budget.xlsx 已就绪
⚠ materials.json 还缺 2 个渠道条目
✗ review-slot：复核时间未约定
```

全是机器能判定的陈述——这正是[验收驱动](/blog/agent-dev-3-acceptance/)那篇的原则：把「符合要求」翻译成可检查的形式。

## 五、什么时候才真该新建

扩展不是万能药。四条红线，踩到任何一条就该另起炉灶：

| 判断维度 | 该新建的情形 |
| --- | --- |
| 交互范式 | 变成纯 GUI 看板 / Web 服务，不再由 Agent 以文本方式推进 |
| 数据底座 | 放弃本地文件加 Git，转向实时多人协作的云端状态 |
| 状态语义 | 大量会签、超时、多角色流转，现有步骤模型根本套不上 |
| 目标用户 | 完全不碰命令行与文本资产的人 |

反过来说：只要还是「本地文本真源 + Git 审计 + Agent 协作 + 状态机闭环」，就该扩展。

## 写在最后

以上是方案推演，**还没实现**——所以这篇文章本身也符合它讲的原则：先写决策简报，再动手。选了什么（原地扩展）、放弃了什么（新建的短期爽感）、为什么（底座复用与心智统一），全部留在纸面上。几个月后回看，这段推演要么被验证、要么被推翻，但不会变成一桩「当时为什么这么决定」的悬案。

下一步：把它变成第一个真实的扩展任务，用最简形态跑起来。
