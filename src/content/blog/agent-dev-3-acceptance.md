「后续代码按照要求进行开发」——这句话不能靠 Agent 的自觉，靠的是把需求翻译成机器能检查的形式。三级翻译：

```text
需求 → 验收标准（AC）          可测试的陈述
AC   → 步骤判据（S1…Sn）        每步做完，哪些 AC 可以被验证
判据 → 门禁（check / review）   工具执行的检查，产出结构化结果
```

## 勾选框不许自己打

验收状态只能由「通过验收的动作」驱动，Agent 手改无效。这条听上去苛刻，其实是整个体系性价比最高的一条：Agent 可以声称自己做完了，但它改不了门禁的输出。**「完成」的定义权在验收机制手里，不在执行者手里。**

顺带一提，AC 是静态的需求断言，跟着需求文档走；进度由步骤计划驱动——两套东西别混在一起，否则 Agent 会用「改勾选框」来假装推进度。

## 测试的两速策略

开发循环里每改一行就跑全量测试，是 Agent 辅助开发最常见的效率黑洞：每一步等一分多钟，二十步下来半天没了。两速策略：

- **开发循环**：只跑与本次改动相关的定向测试；
- **收口**：全量测试、构建、review 一次跑完，而且**只跑一次**。

收口全量的意义在于：它是合并前最后一道独立验证，此时跑的是「整个仓库 vs 整份需求」。定向快、全量真——两头都要，但别放错位置。

## Review 对照的是 Spec

人类 review 的通病是看代码「像不像好代码」；Agent 时代多了一个更基本的对照物：Spec。review 的第一个问题不是「代码好不好」，而是「实现与需求一致吗」——对照验收标准逐条过，再谈风格。

一个实操细节：给 review 的输入是 **Spec 加 diff**，不是 Agent 写的实现总结。总结是执行者写的，Spec 是开工前定下的——用后者审前者，才不会循环论证。

## 复盘要留下东西

收口的最后一环是复盘：这次做对了什么、踩了什么坑、下次什么要先做。踩坑的沉淀升级为编号规则，而且**规则背后必须有能拦截它的机制**——「下次注意」会烂在文档里，「工具会在提交时校验」才会复利。

## 一页 Checklist

三篇浓缩成一页，下次派活前过一遍：

```text
需求
  [ ] 关键决策已问答确认（技术栈 / 部署 / 边界）
  [ ] AC 是可检验的陈述，不是形容词
  [ ] 非目标已写明
执行
  [ ] 计划落盘，步骤原子化，每步有完成判据
  [ ] 接盘笔记四项齐全：目标 / 边界 / 已完成 / 下一步
  [ ] 验收由工具执行，Agent 不能改验收状态
收口
  [ ] 全量测试 + 构建跑过一次且通过
  [ ] Review 对照的是 Spec，不是实现总结
  [ ] 踩坑沉淀为规则或复盘记录
```

Agent 不会替你思考需求，也不该替你定义完成。把这两件事攥在自己手里，Agent 就是最快的执行者。三篇完结，欢迎对照自己的工作流查漏补缺。
