> **动工之前** → [上下文是内存，工程文件是磁盘](/blog/vibe-2-memory-and-disk/) → 模型分级 → 验收门禁 → 复盘即资产。
> 番外：[vibe coding 拼的不是提示词，是工程纪律](/blog/vibe-coding-discipline/)。

「帮我做一个 xxx」是 vibe coding 里最贵的输入。Agent 收到它会立刻开工，而且总能交出点什么——交得太快，你反而没机会在中途发现交出的不是你要的，这个道理在[需求是写给两个读者的](/blog/agent-dev-1-requirements/)里讲过。这个系列不重复为什么，只谈怎么做：五篇文章，对应从动工到复盘的五个阶段。第一篇，动工之前的两道工序。

## 第一道工序：先确认轮子存在

拿到想法，先别让模型写代码，先让它去 GitHub 找同类项目。原因很功利：如果成熟方案已经存在，你的项目可能根本不需要开工；就算要开工，站在成熟方案旁边开工，和从空文件夹开工，是两个难度。

怎么搜不用自己动手，一句话交给 Agent：

```text
我需要开发一个 xxx，它需要包含这些功能：一、… 二、… 三、…
主要在 … 场景使用，希望做到：…。
帮我在 GitHub 寻找类似的项目，输出一份可行性分析：
每个项目的实现思路、star 数、最近一次提交时间、许可证，
最后给出建议：直接复用、参考改造，还是自己从零写。
如果你还有任何问题或建议，先向我提出，解决所有分歧和阻塞后再执行任务。
```

Agent 给出候选之后，有三个维度值得亲手确认，别全信它的总结：

| 维度 | 看什么 | 信号 |
| --- | --- | --- |
| 活跃度 | 最近提交时间、issue 响应速度 | 半年没有动静的项目，慎当地基 |
| 认可度 | star 数、真实使用案例 | star 高但引用全是教程，参考价值打折 |
| 边界 | 许可证、二开友好度 | 想改造的项目被许可证卡住，很扫兴 |

结论无非三种：**直接复用**（多数工具型需求到这一步就结束了）、**参考改造**（大多数正经项目的路线）、**从零写**（确认过没有轮子，或者轮子都不合脚）。每一种都比不调查就开工强。

## 第二道工序：分歧清零

调查结束、决定开工，下一个动作不是写代码，是开方案对话。两条原则：

**方案对话用你手里最强的模型。** 方案是整个项目里杠杆最大的产出——它错了，后面每个执行环节都在放大这个错误。执行可以省钱，策划不省。这笔账第 3 篇细算，这里先记住结论。

**方案落成文档，不落在聊天记录里。** 让最强模型产出一份开发方案：功能边界、技术选型及理由、分阶段的验收标准、明确不做的非目标。涉及 UI 的，让它把界面渲染成可交互的 HTML 预览——对着渲染结果提意见，比用文字想象界面靠谱得多。

然后是整个 vibe coding 里性价比最高的一句话，放进方案对话的结尾：

> 如果你还有任何问题或建议可以先向我提出，解决所有分歧和阻塞后再执行任务。

它的作用不是礼貌，是把对话的主动权翻过来：模型从「猜你要什么」变成「问你它没把握的」。要不要登录？数据存哪？并发多大？这些问题它其实都想问，不问是因为替你默认了答案。**每个没问出口的问题，都会在执行阶段变成一次返工。**

一点经验：别嫌它问得多。方案阶段多答十个问题，好过执行阶段改十轮方向。答完它问的，再把你理解的关键点反向复述一遍让它确认，分歧才算清零。

## 把图纸挂到项目上

方案确认后，把方案对话挂到项目文件夹下（多数工具支持会话深度链接或直接 @ 会话）。从此这个对话的角色就变了：它不再执行任何开发任务，只做两件事——被执行对话引用，以及以后负责审查执行有没有跑偏。

为什么这么较真？因为真正开发起来，执行对话用的是便宜模型、会频繁换窗、会上下文压缩，图纸必须挂在一个不会失忆的地方。

## 动工清单

收成一张清单，新项目开工前过一遍：

- [ ] GitHub 调查做过吗？结论是复用、改造，还是从零写？
- [ ] 方案对话用的是手里最强的模型吗？
- [ ] 方案里有分阶段验收标准和明确的非目标吗？
- [ ] UI 有可交互的预览吗？
- [ ] 「分歧清零」那句话放进结尾了吗？它问的问题都答了吗？
- [ ] 方案对话挂到项目文件夹了吗？

清单过完，才算动工。动工之后第一件事不是写业务代码，是建工程文件——上下文是内存，工程文件才是磁盘。下一篇讲它。
