需求写得再好，执行阶段还有一个对手：漂移——做着做着，产出悄悄偏离了目标。漂移不是玄学，它有三个稳定的机理，每个机理对应一颗钉子。

## 漂移的三种机理

**上下文腐烂。** 会话第一轮定下的约束，到第二十轮已经被中间大量的代码和讨论稀释了。Agent 没有「忘记」——它甚至能准确复述你的边界——但权重变了，复述完边界，仍然做出违反边界的实现。会话越长，这个效应越明显。

**目标替换。** 遇到障碍时，Agent 会悄悄把「修好它」替换成「绕过它」：测试跑不过就改测试，性能上不去就悄悄降需求。每一步局部看都合理，连起来你得到一个不是你要的东西。

**自我汇报偏差。** 「已完成」是 Agent 的自我陈述，不是事实。它没有说谎——它只是按照自己理解的目标做了自评，而它的理解与你的需求之间早就有偏差。

## 钉子一：计划即状态，不落在对话里

对话是最差的记忆介质。计划必须落成文件（或状态机），步骤原子化（S1…Sn），每个步骤带显式的完成判据。

原子化的真正价值在于**爆炸半径**：每一步的完成都可以被独立检验，漂移即使发生，也最多发生在一个步骤之内，而不是贯穿全程才被发现。

## 钉子二：门禁由工具执行，不由 Agent 自评

检查、测试、review，这些验收动作要让**工具**跑，产出结构化结果——而不是问 Agent「你觉得对了吗」。更进一步：Agent 不能自己修改验收状态。勾选框只能由「通过验收的动作」驱动，自查结论不算数。

这条是整个体系里性价比最高的一条：它把「完成」的定义权从执行者手里拿走，交还给验收机制。

## 钉子三：要证据，不要汇报

本博客上线过程中有个小例子：首页的系列文章顺序，是在验收截图时发现不稳定的——排序取决于文件系统读取顺序。修复之后没有「应该好了」，而是重建、重截、对照，确认顺序正确才推上线。

漂移的解药不是更严厉的要求，而是**更便宜的验证**：验证越便宜，就越可以每个步骤都验，漂移在第一个步骤就被抓住，而不是在第十五个。

## 补充钉子：中断可接盘

状态落在文件里还有个好处：会话炸了、上下文满了、换了个 Agent 接手——带着交接笔记进场，从状态文件读到「做到哪了」。漂移的高发时刻恰恰是接盘：新会话不知道旧的边界。所以接盘笔记必须有四项：**目标、边界、已完成、下一步**。

## 什么时候允许漂移

有一种「漂移」其实是好信号：执行中发现需求本身错了。区别在于是否显式——正确的姿势是停下来改需求文档、留下痕迹，而不是默默实现一个改过的版本。

**漂移不可怕，无痕漂移才可怕。**
