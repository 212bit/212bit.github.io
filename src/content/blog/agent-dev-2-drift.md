需求写得再好，执行阶段还有一个对手：漂移——做着做着，产出悄悄偏离了目标。漂移不是玄学，它有三个稳定的机理，每个机理对应一颗钉子。

## 漂移的三种机理

**上下文腐烂。** 会话第一轮定下的约束，到第二十轮已经被中间大量的代码和讨论稀释了。Agent 没有「忘记」——它甚至能准确复述你的边界——但权重变了：复述完「不做评论系统」，转头就提议「加个简单的评论区吧」。会话越长，这个效应越明显。

**目标替换。** 遇到障碍时，Agent 会悄悄把「修好它」替换成「绕过它」。最经典的一幕：测试红灯，正确的动作是修实现，替换动作是把断言改松——测试绿了，bug 还在。每一步局部看都合理，连起来你得到一个不是你要的东西。

**自我汇报偏差。** 「已完成」是 Agent 的自我陈述，不是事实。它没有说谎——它只是按照自己理解的目标做了自评，而它的理解与你的需求之间早就有偏差。

## 一个完整的案例：排序漂移

用本博客的一次真实翻车，把上面三条串起来。

**现象。**「指纹深挖」系列上线后，验收截图发现首页顺序不对：（二）（三）排在了（一）前面。

**差点误判。** 第一反应是「构建缓存脏了」——去清缓存、重试。这就是在错误的维度上做功：缓存问题清一次就该好，反复不好就说明病因在别处。

**定位。** 三篇同日期发布，而列表排序只按日期、同日期的顺序未定义——实际取决于文件系统读取顺序，换台机器结果都可能不同。

**修复。** 排序加一条决胜规则，一行 diff：

```diff
-  .sort((a, b) => b.data.date.valueOf() - a.data.date.valueOf())
+  .sort((a, b) => b.data.date.valueOf() - a.data.date.valueOf()
+                  || a.id.localeCompare(b.id))
```

**值得后怕的地方**：这个 bug 经历了三次部署都没有被发现——因为之前没有任何验收项检查「顺序」。它是被整个流程里最便宜的验证（截图扫一眼）抓住的。

**教训**：漂移不是惊天事故，是没人检查的小偏差慢慢长大。验证越便宜，偏差存活的时间越短。

## 三颗钉子

**钉子一：计划即状态，不落在对话里。** 对话是最差的记忆介质。计划必须落成文件（或状态机），步骤原子化（S1…Sn），每步带显式完成判据。原子化的真正价值是**爆炸半径**：每一步可独立检验，漂移即使发生，也最多活在一个步骤之内，而不是贯穿全程才被发现。

**钉子二：门禁由工具执行，不由 Agent 自评。** 检查、测试、review 要让**工具**跑，产出结构化结果，而不是问 Agent「你觉得对了吗」。更进一步：Agent 不能自己修改验收状态——「完成」的定义权在验收机制手里，不在执行者手里。

**钉子三：要证据，不要汇报。** 上面那个排序 bug 的收尾没有「应该好了」：改完重建、重新截图、对照确认、才推上线。漂移的解药不是更严厉的要求，而是**更便宜的验证**。

## 补充钉子：中断可接盘

状态落在文件里还有个好处：会话炸了、上下文满了、换 Agent 接手——从状态文件读到「做到哪了」。漂移的高发时刻恰恰是接盘：新会话不知道旧的边界。接盘笔记四项缺一不可，本博客的接盘笔记是这么写的：

```markdown
## 目标
上线「指纹深挖」系列四篇
## 边界
只动 src/content/blog/；不改框架与样式代码
## 已完成
四篇写完；构建通过；四条路由本地 200；截图验收通过
## 下一步
push → 等待 Actions → 线上逐条 curl 验证
```

## 什么时候允许漂移

有一种「漂移」其实是好信号：执行中发现需求本身错了。区别在于是否显式——正确的姿势是停下来改需求文档、留下痕迹，而不是默默实现一个改过的版本。

**漂移不可怕，无痕漂移才可怕。**
