> 本文是「Vibe Coding 实战手册」第 2 篇（共 5 篇）：
> [动工之前](/blog/vibe-1-before-coding/) → **上下文是内存，工程文件是磁盘** → 模型分级 → 验收门禁 → 复盘即资产。
> 番外：[vibe coding 拼的不是提示词，是工程纪律](/blog/vibe-coding-discipline/)。

第二天早上，你开了个新对话说「继续昨天的开发」。模型很热情地问：项目在哪？做到哪了？之前定的什么技术栈？——不是它笨，是它的记忆断电了。这一篇讲怎么给它配一块磁盘。

## 对话窗口是内存

上下文窗口的一切特性都像内存：读写快，断电即失。而断电有三种方式，每一种都稀松平常：新开对话（必然发生）、上下文压缩（对话一长必然触发）、换平台换模型（跨模型协作时必然发生）。

压缩可以理解成 swap：核心结论能留下，细节全糊。昨天确认的接口签名、踩过的报错、你否掉的三个方案，压缩两轮之后只剩一行「已完成部分开发工作」。拿这行字接活的模型，只能靠猜。

所以原则只有一条：**凡是需要活过当前对话的信息，必须落盘。** 问题只剩两个：往哪写，怎么读。

## 磁盘的最小集合

工程文件不是越多越好。读帖笔记里介绍过热帖的九文件完整形态，我的建议是从小起步：两个文件就能开工，项目长到哪，拆到哪。

| 文件 | 回答什么问题 | 什么时候读 | 什么时候写 |
| --- | --- | --- | --- |
| AGENTS.md | 这个项目的活怎么干 | 每个新对话开工前 | 规则变化时（低频） |
| NOW.md | 进度到哪、下一步是什么 | 每个新对话开工前 | 每个任务收尾时（高频） |

这两个是起步配置。项目长出下面这些需要时，再逐个拆出来：

| 文件 | 什么时候需要它 |
| --- | --- |
| PROJECT_INDEX.md | 文件多到「去哪找」本身成了问题 |
| RUNBOOK.md | 构建运行步骤复杂到记不全 |
| DECISIONS.md / RISKS.md | 出现被否掉的方案、需要盯防的风险 |
| MAP.md / history/ | 多环境多版本，或有值得归档的过程 |

但要说清楚：文件本身没有用，**读写纪律才有用**。下面四段是这套体系真正的成本所在。

## 读的纪律：按需检索，禁止通读

最重要的一条规则，写进 AGENTS.md：找东西必须走「索引 → 关键词 → 命中片段」，禁止默认读全文件。

理由有两层。第一层是钱：工程文件会越长越大，每轮对话全文喂入，token 成本跟着对话轮数平方级上涨。第二层更要命，是判断力：一坨与当前任务无关的内容灌进窗口，注意力被稀释，模型开始忽略你三个月前写下的关键约束——**上下文越满，指令遵从越差**。

可以直接照抄的读取规则：

```text
- 按当前任务选择资料，不因「文件存在」就读
- 先查索引或搜索，定位到章节/条目/函数，读命中片段及必要上下文
- 信息足够即停，不连续分段通读全文
- 索引是路由，不是必读清单；历史、日志、依赖目录不默认读取
```

## 写的纪律：单一权威来源

读有纪律，写更有。四条：

**每类事实只有一个权威来源**，别处只放摘要加链接。两个文件都记「当前进度」，它们迟早打架，接手的模型不知道信谁。

**只改当前状态，不叠加快照。** NOW.md 里的旧进度直接修订或归档，不要每次追加一段——三个月后没人能分清哪段还有效。

**区分事实、计划、建议、待核实。** 「代码写完了」和「测试通过了」是两码事，混着写，接手的模型会把计划当成既成事实往下盖楼。

**写结论和证据入口，不贴流水账。** 把聊天记录整段粘进工程文件是最常见的反模式：文件膨胀十倍，可检索性归零。

| 反模式 | 后果 | 替代做法 |
| --- | --- | --- |
| 聊天记录整段入库 | 文件膨胀，检索失效 | 写结论，附证据入口 |
| 只追加不修订 | 新旧快照打架 | 改当前状态，旧内容归档 |
| 多个文件记同一事实 | 数据不一致 | 单一权威来源 |
| 文档与代码漂移 | 接手模型被误导 | 定期对照代码现状 GC |

最后一条单独说：**文档会腐烂，这是它的宿性**。项目迭代若干轮之后，安排一个维护任务，让模型对照代码现状清理工程文件、删掉过时信息。文档是缓存，是缓存就得有 GC。

## 换窗：给内存主动断电

落盘之后，你就获得了单对话之外的自由：**执行对话是消耗品，用完就换。**

一个执行对话的合理生命周期：做**一个阶段**的任务，一个半小时上下，或者经历四五次上下文压缩——任一到了就换。换窗不是损失，是止损：长对话后期的模型，响应变慢、约束遵从变差、开始自作主张，留着只会返工。

换窗 SOP 就两步，合计一分钟：关窗前，让旧对话把进度、阻塞、下一步更新进 NOW.md；开新窗，让新对话读 AGENTS.md 和 NOW.md 里的任务章节，复述确认后再接任务。新对话头几轮的「慢」，换的是全程不背着上一窗的疲劳上下文干活。

## 为什么这套东西值得机器来管

写到这你会发现，文件分工、检索规则、状态修订——全是纪律，而纪律靠人肉维持，必然松懈。我自己把这套东西做成了工具 DocPath：spec / plan / breadcrumb 分工取代上面那堆手工 md，检索走 token 预算，收尾有门禁强制对账（设计与取舍见[渐进式分层与上下文经济学](/blog/docpath-2-progressive-context/)那篇）。手工维护和机器维护都对，区别只是：靠自觉，还是靠流程。

## 写在最后

内存断电不可怕，可怕的是你以为它还在。把该活下来的写进磁盘，让模型按需读——多会话开发的「不失忆」，全部秘密就这两句。
