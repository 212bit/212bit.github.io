## 主从分工：别让主角干杂活

状态机和渐进式让**单个**智能体靠谱了，但两个新问题随之而来：主会话的上下文越干越胖；多个智能体同时干活会互相踩。

前者的解法是 master-worker：主会话只保留最小职责——看路由、派步骤、验结果；深读大文件、长篇编辑这类上下文重活，派给专职的工人子代理。工人带着交接笔记进场，干完一步 `step-pass` 退出。**中间产物落在文件里，而不是对话里**——文件才是记忆介质，对话只是调度信道。

## worktree：让多个智能体不打架

并发的答案直接借用 Git 的原生能力：每个智能体一棵 worktree，互不干扰地跑在同一个仓库里。

- **共享的**：`.docpath/backlog/`（需求池）与 `.docpath/rules/`（规范库）——领任务要看到同一个池子，规范要全局一致；
- **隔离的**：`.docpath/workspace/`（`state.json`、事件流）与任务运行时——每个工作树一份，互不覆盖；
- **提交时汇合**：`docpath commit` 只把任务证据（spec、plan、归档）提取进 Git 历史，运行时噪音全部排除在外。

当然有坑：依赖目录（node_modules）不是天然隔离的，共享不当会写穿主干的依赖树，而且 git 看不见这种漂移。这个坑最后变成了一条编号规则和一个 `worktree doctor` 体检命令——正好引出本篇的主题。

## 规则是踩坑的复利

DocPath 里我最喜欢的机制是 R-编号制度：**每次翻车，沉淀为一条机器可校验的编号规则**。

举三个真实的：

- **R-460**：不要每做完一步都重跑路由命令——生命周期命令自带 `next_hint`，信任它（这是「上下文经济学」的制度化）；
- **R-238**：worktree 下的资源共享模型——哪些目录共享、哪些隔离，白纸黑字写清楚；
- **R-467**：依赖不隔离——worktree 里装依赖会写穿主干，合并前必须跑 doctor 检查。

规则和散文的区别在于：**散文靠智能体「记得」，规则靠机制「拦截」**。R-460 背后是自循环守卫，R-467 背后是 doctor 命令。能被拦住的才叫规则，其余只是愿望。

Fail-safe 是同一哲学的延伸：防脱水 HEAD、防冲突、防重要源码未追踪漏交；提交自动带上 Agent Co-Author 签名——人机协作的每一行代码，作者关系是诚实的。

## 写在最后

三篇写完，回头一看，DocPath 没有发明任何新哲学。它做的事情，是把工程里的老手艺——原子提交、验收驱动、文档同步、上下文最小化——翻译成机器可执行的约束，让智能体和人类走在同一条铁轨上。
