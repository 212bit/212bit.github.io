最近一年多主要精力在做一个防关联指纹浏览器项目。这篇文章不聊具体实现，聊聊做到现在沉淀下来的几个核心理解。

## 防关联的本质：不是隐藏，而是自洽

很多人对指纹浏览器的第一反应是「让网站认不出我」。做深了才发现方向反了——**目标不是让浏览器消失，而是让它成为一个可信的、独立的人**。

平台风控看的从来不是单点参数，而是**参数之间的一致性**：

- UA 声称是 Windows，但 WebGL 渲染器暴露了 macOS 的 Metal；
- 时区设在纽约，语言列表却是 `zh-CN` 打头；
- 屏幕分辨率是 4K，字体列表里却没有一款 Windows 自带字体。

任何一处矛盾，单独看都不致命，叠加起来就是「这个环境在撒谎」的信号。所以防关联的第一性原理是：**给定一个身份人设（OS、硬件、语言、时区），所有指纹维度必须从这个假设出发逻辑自洽地推导出来**。

## 内核决定上限，参数体系决定下限

基于 Chromium 内核改，指纹的「原材料」来自两层：

1. **运行时内核层**——Canvas、WebGL、AudioContext 这些采集点的底层行为要可控。我们在这层做了统一的运行时内核（内部叫 RoxyChrome），保证注入的参数是内核启动时就生效的，而不是页面加载后才打的补丁；
2. **参数配置层**——把上百个可调维度收进一套统一的配置体系（`lumi.conf`），每个身份一份配置文件，可导出、可迁移、可版本管理。

这层的经验教训是：**参数体系的表达力决定产品的上限**。早期散落在代码各处的开关，后来全部收敛到配置文件之后，才谈得上「批量管理几百个身份」这种需求。

## 审计站是校验器，不是记分牌

browserscan、pixelscan、creepjs、browserleaks 这些审计站，价值不在于那个百分比分数，而在于它们把检测维度摊开给你看。我们内部把审计站的扣分项当成测试用例的输入，高频翻车的几类：

- **WebGL 异常**：渲染器/厂商字符串与 OS 不匹配，或明明说自己是集显却报了独显的参数；
- **版本不同步**：UA 里的 Chrome 版本和 JS 引擎行为特征对不上（老版本 UA 配新内核行为）；
- **硬件参数矛盾**：内存、核数、分辨率组合出了市面上不存在的机型；
- **CrawlerJS / creepjs 的谎言检测**：API 之间互相引用校验，patch 不彻底反而暴露 patch 的痕迹。

每换一次内核版本，都要把审计站全量过一遍——这套流程我们也做成了内部的排查工作流，扣分项能定位到具体参数。

## 自动化不是外挂，是接口

指纹浏览器如果只能手动点开窗口，价值就少了一半。批量场景的本质是「程序化地创建、启动、接管、释放浏览器身份」，所以架构上一开始就把 REST API 和 MCP 服务当成一等公民：

- 用 REST API 做生命周期管理（建环境、开窗口、关窗口）；
- 用 MCP 让 AI 智能体可以直接「接管」一个窗口做操作；
- 底层通过 CDP（Chrome DevTools Protocol）对接 Playwright / Puppeteer / Selenium。

一个验证过的体感：**当创建一个隔离环境只需要一次 API 调用时，工作流的形状就变了**——从「我在操作浏览器」变成「我在编排身份」。

## 小结

指纹对抗是个动态博弈，今天的结论明天可能就过期。但有几件事我认为不会变：

1. 自洽性 > 隐藏性；
2. 内核深度决定真实度上限；
3. 一切「看起来可信」最终都要能用审计站复现验证；
4. 接口化（API / MCP）是把工具变成生产力杠杆的关键。
