## 一句话需求的问题

「帮我做一个博客」——这种需求交给 Agent，它会立刻开工，而且**总能交出点什么**。问题在于它用什么填补你没说的部分：它的默认假设。部署在哪？什么风格？要不要后台？每个你没回答的问题，都被一个默认值顶上，每个默认值都是未来的返工。

人类团队里这道工序叫需求评审；和 Agent 协作，没有产品经理替你把关——**你就是需求评审**。

## 需求有两个读者

同一份需求文档，其实服务两个读者：

- **现在的 Agent**：需要无歧义的边界与验收标准，写给它的部分可以意会的越少越好；
- **三个月后的 Agent**（以及三个月后的你）：上下文早就丢了，靠文档接盘。

实操上四件事比篇幅重要：

### 一、先问答，再动工

模糊的需求先别写，先问。本博客开工前确认了两个问题：用什么技术栈、部署到哪——两个答案把后面所有决策锚定了。问答的成本是一轮对话，跳过的成本可能是整站重做。

### 二、验收标准先行

把「做了什么」换成「怎样算做对了」。验收标准是可检验的陈述，不是形容词：

```text
❌ 首页要美观，性能要好
✅ 首页展示最新 5 篇文章，列表在窄屏下不破版
✅ 同日期文章按固定规则稳定排序
```

形容词由 Agent 解释——它总能自圆其说；能被检查的状态才能被验收。

### 三、不做什么，也要写

需求文档里最值钱的往往是「非目标」。本博客明确写了：不做后台、不做评论系统、不做手动暗色开关。Agent 对「顺便多做一点」有天然冲动，边界不写下来，范围就被它替你扩张了。

### 四、动架构前先写决策简报

换技术栈、改契约、引入长期成本的动作，先写一段：要解决什么问题、选了什么、放弃了什么、为什么。决策简报不是仪式感——它是三个月后防止「当时为什么这么设计」变成悬案的唯一证据。

## 需求的重量要分级

不是所有需求都配得上完整 Spec。改个错别字和改架构走同一个流程，结局要么是流程被绕过，要么是效率被杀死。按变更风险分级：微型任务一句话加验收标准即可；动架构的，才上需求、设计、计划的完整三件套。

## 一个真实的例子

本博客最初的需求单其实很短：展示项目信息与技术感悟、中文、可长期维护、部署免费。展开之后变成：Astro 加 GitHub Pages、五个页面、一个设计方向、几条验收项。这个早期结构后来兑现了——三篇、四篇的系列文章陆续加进内容管道，**没有为此重构过一行框架代码**，因为「Markdown 进、静态站出」的形状在需求阶段就定死了。
