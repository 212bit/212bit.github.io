## 一句话需求的问题

「帮我做一个博客」——这种需求交给 Agent，它会立刻开工，而且**总能交出点什么**。这正是危险所在：交出的速度太快了，快到你没有机会在中途发现它交出的不是你要的。等第三轮迭代才看清方向偏了，沉没成本已经让你倾向于「就这样吧」。

问题出在它用什么填补你没说的部分：它的默认假设。部署在哪？什么风格？要不要后台？每个你没回答的问题，都被一个默认值顶上，每个默认值都是未来的返工。

人类团队里这道工序叫需求评审；和 Agent 协作，没有产品经理替你把关——**你就是需求评审**。

## 需求有两个读者

同一份需求文档，其实服务两个读者：

- **现在的 Agent**：需要无歧义的边界与验收标准，能意会的部分越少越好；
- **三个月后的 Agent**（以及三个月后的你）：上下文早就丢了，靠文档接盘。

实操上四件事比篇幅重要。

### 一、先问答，再动工

模糊的需求先别写，先问。本博客开工前只确认了两个问题：用什么技术栈、部署到哪——两个答案把后面所有决策锚定了。问答的成本是一轮对话，跳过的成本可能是整站重做。

判断哪些必须问：**凡是两个合理的人会给出不同答案的决策，就值得问一句**。风格可以给 Agent 发挥，平台和框架不行。

### 二、验收标准先行

把「做了什么」换成「怎样算做对了」。验收标准是可检验的陈述，不是形容词——形容词由 Agent 解释，它总能自圆其说。本博客真实的验收标准长这样：

| ❌ 形容词（Agent 来解释） | ✅ 可检验（机器来判定） |
| --- | --- |
| 设计要有辨识度 | 暖纸底 + 衬线标题 + 全站唯一强调色；暗色跟随系统自动切换 |
| 网站要快 | 纯静态输出、无运行时 JS 框架；构建零报错 |
| 文章要好发布 | 新建 .md + git push，一分钟内自动上线，不登录任何后台 |
| 列表不会乱 | 同日期文章按固定规则稳定排序，换机器结果一致 |

第四条后来真的救过场——它在验收时抓出了一个排序 bug（下一篇完整讲）。

### 三、不做什么，也要写

需求文档里最值钱的往往是「非目标」。本博客明确写了：不做后台、不做评论系统、不做手动主题开关。Agent 对「顺便多做一点」有天然冲动，边界不写下来，范围就被它替你扩张了。三个月过去，这三样还是没做——不是忘了，是白纸黑字。

### 四、动架构前先写决策简报

换技术栈、改契约、引入长期成本的动作，先写一段。本博客的选型决策简报当时就这么几行：

```text
决策：框架选 Astro，放弃 Hugo / Hexo
问题：要一个 Markdown 优先、可长期维护的静态博客
对比：Hugo 构建快但定制要写 Go 模板；Hexo 生态老、定制绕；
     Astro 组件即 HTML，内容集合天然贴合「一堆 Markdown」
代价：构建速度不如 Hugo（实测 1.4 秒，可接受）
放弃：Hexo 的中文主题生态
```

决策简报不是仪式感——它是三个月后防止「当时为什么这么设计」变成悬案的唯一证据。

## 需求的重量要分级

不是所有需求都配得上完整 Spec。同一个流程服务所有体量，结局要么是流程被绕过，要么是效率被杀死。按变更风险分级：

- **微型**（diff 几十行内：错别字、单点配置）——一句话需求 + 一条验收，直接做；
- **小型/中型**（百行上下）——需求 + 简短计划，步骤不必细分到 S1…Sn；
- **架构级**（换框架、改契约、跨模块）——需求、设计、计划完整三件套，外加决策简报。

## 一个真实的例子

本博客最初的需求单其实很短：展示项目信息与技术感悟、中文、可长期维护、部署免费。展开之后变成：Astro 加 GitHub Pages、五个页面、一个设计方向、四条验收标准。这个早期结构后来持续兑现——七个系列文章陆续进内容管道，**没有为此重构过一行框架代码**，因为「Markdown 进、静态站出」的形状在需求阶段就定死了。

需求写清楚，只是把方向钉住了；执行阶段的敌人是漂移——下一篇讲它为什么发生、怎么钉住。
