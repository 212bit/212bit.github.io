排查「指纹浏览器被审计站判异常」，最大的弯路是：**在错误的维度上反复试验**。审计站看的东西，往往不是你以为的那个东西。这篇用四个真实案例讲清楚这件事。

## 先立三条铁律

**一、先测基准，再改任何东西。** 永远先在同一台机器上跑一次真实 Chrome，记录同项输出。没有基准，你无法区分「配置错了」和「真实 Chrome 也这样」。我们项目历史上两次重大误判，都源于没立基准就下结论。

**二、审计判定 ≠ 你看到的字符串。** 比对 WebGL 时，`vendor` / `renderer` 字符串完全一致，仍可能被判异常——因为 browserscan 对**渲染像素做哈希**，不是读字符串。

**三、先分类，再动手。** 问题只有三种，处置完全不同：

| 类型 | 特征 | 处置 |
| --- | --- | --- |
| 配置不自洽 | 参数互相矛盾 | 改配置 |
| 内核能力缺陷 | 同参数换内核结果不同 | 升级内核 |
| 判定抖动 | 同配置多实例结果分裂 | 先复测，别动参数 |

## 案例一：报「版本不同」，改 UA 没用

页面显示 `Browser Version 148.0.7778.215 异常`，直觉是「版本号格式错了」。真因完全不同：profile 的 UA 写的是 142，而内核的 Client Hints **如实**返回 148——

```text
navigator.userAgent   = ... Chrome/142.0.0.0   ← profile 指定的
userAgentData.brands  = 148                    ← 内核如实回答
uaFullVersion         = 148.0.7778.215         ← 内核如实回答
```

审计站读的正是 Client Hints 的值，它和 UA 互相打脸 → 判 UA 篡改。**改 UA 字符串格式没有任何用**，唯一解法是让 profile 的声称版本跟随内核真实版本。三个主版本必须一致：内核 == UA == 档案记录。

## 案例二：canvas 页说你是一台 Mac

`navigator.platform` 明明已经伪装成 `Win32`，browserleaks 的 canvas 页却坚持「识别出 Mac」。对照测试一锤定音：

```text
measureText('mmmmmmmmmmlli').width
  指纹窗口（Windows 人设）: 125.9521484375
  裸 Chromium（真机 Mac） : 125.9521484375   ← 逐字节相同
```

内核伪装了 platform 和 UA，却没伪装 **canvas 的文字渲染引擎**——macOS 宿主上跑 Windows 人设，canvas 仍在走 CoreText，渲染结果与真机 Mac 完全相同，于是落进同一个签名。browserleaks 的 Signature Stats 还是**众包直方图**：直接调它的 API 能看到该签名被 115 台真 Mac、21 台 Windows 提交过，页面按多数派显示。

换 seed 无效（变的只是噪声，渲染引擎没变）；关掉 canvas 噪声更糟（直接返回宿主真实渲染值）。这类问题的唯一规避是让**声称平台与渲染引擎一致**——配置层解决不了的，要如实告诉用户，而不是继续让他调参数。

## 案例三：字体枚举的白名单漏洞

字体伪装机制本身工作良好：非白名单的 macOS 独有字体，27 个里泄漏 **0** 个。但 `IsBasicFont()` 白名单让 `Helvetica Neue`、`Lucida Grande`——两个如假包换的 macOS 独有字体——**提前返回、完全跳过伪装**，结果 9 个里泄漏 6 个。

这类「机制正常、白名单破功」的问题，最迷惑人的地方是换 seed 无效（判定发生在 seed 之前）、加参数无效（那个参数根本不存在，Chromium 对未知的 `--fingerprint-*` 静默忽略）。定位它靠的是把内核二进制里的 switch 表 `strings` 出来核对——**别猜参数，去二进制里查它存不存在**。

## 案例四：参数全对，WebGL 仍异常

字符串全对、仍报「WebGL 異常」，就该测第二层了——清屏后读回像素：

```js
const gl = canvas.getContext('webgl', {preserveDrawingBuffer: true});
gl.clearColor(0.5, 0.5, 0.5, 1); gl.clear(gl.COLOR_BUFFER_BIT);
const px = new Uint8Array(256*256*4);
gl.readPixels(0, 0, 256, 256, gl.RGBA, gl.UNSIGNED_BYTE, px);
// 统计偏离 128 的像素数
```

同一台机器的实测：真实 Chrome 偏差 **0** 像素；内核 142 偏差 7 像素，browserscan 95%；内核 148 偏差 **0**，100%。结论清晰：GPU 模拟精度是内核缺陷，**只能升级内核解决**，改任何参数、换任何 seed 都无效。（顺带：148 修复了它，又引入了新的 GPU 回归——上游 issue 里有记录。查上游 issue 避免重复排查，也是方法论的一部分。）

## 两个常被误诊的环境问题

**「時區不符」先查代理。** 同一份配置，有日本代理时 100%，代理一关掉到 85%（時區 -10% + 版本 -5%）。时区与 IP 地理的一致性是网络层问题，先看代理状态，再看指纹配置。

**「判定抖动」用多实例法。** 启 4–6 个参数逐字节相同的实例分别过审计：结果分裂就是抖动（服务端会话状态，清缓存实测无效）；结果一致但分低，才是真缺陷。

## 收口

改完任何东西：复跑至少三轮再下结论；用产品自身的启动链路复验，而不是只信手写测试脚本；记录改动前后的值和问题归属（配置 / 内核 / 抖动）。**指纹排查的产出不是「这次过了」，而是「知道为什么」**——下一篇讲怎么从一开始就让它过：自洽人设工程。
