过去一年把编码智能体（Claude Code、Codex 这类）深度嵌进了日常工作流，从「问问答答」进化到「派活收活」。这篇记几条真正花钱（token）买来的感悟。

## 一、上下文是稀缺资源，要像管内存一样管它

智能体干活翻车，多数时候不是「不够聪明」，而是**上下文被撑爆了**：塞进一堆无关文件、读了不该读的大文档、被历史对话里的噪音干扰。

对策很朴素，但执行要狠：

- 给智能体喂**摘要**而不是原文档——机器路由（`next --agent` 这类命令）返回的几行结论，比让它通读整份 README 有效得多；
- 用 token 预算去检索（`context --smart --max-tokens 2000` 这种），而不是「你去把代码库扫一遍」；
- 会话膨胀就轮换：让子代理带着交接笔记接盘，主会话永远保持轻。

把这些做法沉淀下来之后最大的变化是：**同一个模型，同一类任务，成功率高了一大截**。差别全在喂了什么。

## 二、步骤原子化：让「声称完成」变得可验证

「帮我实现 X」这种大而化之的委派，最容易得到的是「看起来完成了」的回复。后来改成把任务拆成显式的步骤（S1…Sn），每一步有明确的完成判据，做完一步过一道门禁（check → review），情况就完全不同了。

本质上是把**信任问题转换成验收问题**：我不需要相信智能体的自我汇报，只需要看每一步的验收证据。这和人类工程师的 code review 是同一个道理——只是机器更需要显式的验收标准，因为它不会「不好意思」。

## 三、主从分工：别让主角干杂活

多步骤任务里最贵的操作是主会话亲自深读大文件。现在我的默认形态是：

- **主会话（master）**：只看路由和进度，保持上下文干净；
- **工人子代理（worker）**：领一个明确的步骤，带着任务笔记进场，干完退出；
- 中间产物（决策、坑、交接说明）落在文件里，而不是对话里。

对话记录是最差的记忆介质，文件才是。这也是为什么文档驱动的工作流（我们内部的 DocPath，把文档当有限状态机用）和智能体是天作之合：**文档既是给人的说明，也是给机器的状态存储**。

## 四、规则要写成机器可校验的约束

给智能体写规范，散文式的「请注意保持代码整洁」基本无效。有效的规则长这样：

```text
- 禁止手改 AC 勾选框（工具会在提交时校验）
- 禁止在开发循环里跑全量测试（只允许单文件定向测试）
- 触碰核心引擎的任务禁止走快速通道（按 diff 体积强制分级）
```

每条规则背后都有一个**能拦住它的机制**。智能体不缺阅读理解能力，缺的是把「应该」变成「不能」的硬约束。

## 五、一点更大的图景

把这些实践连起来看，会发现一个趋势：**软件工程的经典方法没有被 AI 推翻，反而变得更必要了**——原子提交、验收驱动、文档同步、上下文最小化，这些老手艺在人和机器协作时收益都被放大了。

AI 没有改变「什么是好的工程」，只是把做坏工程的成本降到了零，把做好工程的回报也放大了。

剩下的，就是把手艺练好。
